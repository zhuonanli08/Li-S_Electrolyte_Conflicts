# 断点继续与恢复开销

沿用当前原有 thread 的需求、已授权范围、偏好与已完成工作。不要要求用户重新提供上下文中已有的需求，不新建替代 thread。新消息默认是对原任务的补充，除非用户明确取消或替换目标。

## 恢复检查

先利用当前上下文、压缩摘要与最近进度记录确定目标和实际中断点，再做最小必要核对：

1. 检查当前 Git 状态、`git diff --stat`，按本任务相关路径读取必要的 diff；非 Git 任务注明不适用。
2. 确认已修改文件、已产出结果、完成项、未完成项、最后失败动作以及已有验证结果。并行任务存在时区分其所有权，不覆盖或提交无关改动。
3. 已有可信的完成和验证证据就复用。仅在文件后来变化、验证失败或存在具体未解决疑点时重跑对应步骤；不要重做已确认完成的提取、分析或开发。
4. 从最后实际未完成的步骤继续，执行既有授权内的剩余工作与必要验证。工具限制、额度或缺失必需信息造成阻塞时，保存准确断点并说明，不能把部分结果标为完成。

不要为恢复本身全量重读仓库或历史。优先精确路径、变更摘要、已保存检查点；缺少影响决策的信息时再读取最小相关片段。此前授权继续有效，但不扩大到无关操作。

## 分开记录

在项目已有进度记录中或紧邻本次结果目录维护一份简短的恢复日志，沿用已有日志，不为每次继续新建副本。按发生的动作记录，不为记录而重复执行。至少包含日期、动作类别、动作与结果：

- **恢复开销**：仅因中断而需要的上下文重建、状态/diff核对、重读进度、恢复或重新派发已中断的代理。注明其中哪些检查同时发现了真实新变更。
- **正常任务工作**：完成剩余内容、处理真实的新要求或新变更、修复问题、执行本来就需要的验证、交付成果。
- 若同一调用含两类工作，按动作说明区分；无法可靠拆分的标为混合，不强分时间或 Token。

完成后输出简短的《跨天恢复开销报告》：列出恢复工作、正常继续工作，以及只有中断才额外发生的动作。若仍被阻塞，只输出阶段记录并保留待办，不宣称原任务已完成。

## Token 统计

仅报告工具、平台或可信运行日志实际提供的 Token 数据，并写清统计范围、是否包含子代理、缓存或历史轮次。账户额度百分比、上下文占用率、输出截断提示不是本次任务的 Token 用量。

没有实际统计时明确写“无法取得可核验的 Token 使用统计，未估算”。不得按字数、文件大小、工具次数、时长或模型常识推算 Token，也不能把线程总量任意分摊给恢复动作。没有同任务连续完成的实测对照时，不能量化中断带来的净额外 Token 消耗。

不要为了这个测试读取无关文件、扫描其他对话、运行额外分析或制造对照任务。
